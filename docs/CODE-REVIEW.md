# Частина 2. Рев'ю коду

Фрагмент коду, згенерований AI-інструментом за тікетом «нарахувати бонус на баланс гравця»
в іншому проєкті. Розгляд без запуску — як PR колеги.

```php
// routes/api.php
Route::get('/players/{player}/credit-bonus', [WalletController::class, 'creditBonus']);
```

```php
// app/Http/Controllers/WalletController.php
public function creditBonus(Request $request, Player $player)
{
    $player->balance += $request->amount;
    $player->save();

    return response()->json(['success' => true, 'balance' => $player->balance]);
}
```

```js
// resources/js/components/BonusCredit.vue (фрагмент методу)
async creditBonus(amount) {
  const response = await axios.get(`/api/players/${this.player.id}/credit-bonus`, {
    params: { amount }
  })
  this.player.balance = response.data.balance
}
```

## Бекенд

### Блокери

**1. Немає ні автентифікації, ні авторизації.** На роуті не висить жодного middleware —
ендпоінт відкритий будь-кому без токена. Поверх цього `Player $player` резолвиться напряму
з роут-параметра через route-model-binding. Будь-хто, підставивши чужий `player_id` в URL, може нарахувати бонус
довільному гравцю. Гравець має братися з автентифікованого користувача (`$request->user()`),
а не з URL — параметр `{player}` взагалі зайвий.

**2. `$request->amount` не валідується.** Немає перевірки типу, знаку, меж. Наслідки:
- від'ємне число → **списує** кошти замість нарахування;
- немає верхньої межі → одним запитом можна нарахувати будь-яку суму;
- рядок замість числа: у PHP 8 нечислова строка в арифметиці кидає `TypeError` (тобто 500
  замість помилки валідації), а «5abc» — warning і мовчазне 5;
- відсутнє значення → `null + число` = warning/помилка залежно від версії PHP.

**3. GET для операції, що змінює стан.** Нарахування — мутація, тому має бути POST/PATCH,
а не GET. Наслідки конкретно GET тут:
- браузери й проксі можуть **кешувати** відповідь;
- **prefetch** (браузер, антивірус, лінк-прев'ю в месенджерах) може викликати ендпоінт без
  відома користувача;
- сума й player_id потрапляють у **query string** → логи сервера, історію браузера,
  Referer-заголовок;
- за **сесійної** автентифікації (Sanctum у SPA-режимі) ендпоінт стає вразливим до CSRF
  через звичайний `<img src="...">`: Laravel перевіряє CSRF-токен лише на POST/PUT/PATCH/DELETE,
  на GET — ніколи. Застереження: цей роут лежить у `routes/api.php`, де сесії й `VerifyCsrfToken`
  не підключені взагалі, тож за токен-авторизації вектор не спрацює — але тут авторизації
  немає жодної (пункт 1), тому запит і так відкритий кожному.

**4. Race condition (lost update).** `$player->balance += $request->amount; $player->save();` —
read-modify-write без блокування рядка й без транзакції. Два паралельні запити читають той
самий старий баланс, і один інкремент губиться. Потрібен `DB::transaction()` з
`lockForUpdate()`, або атомарний `increment()`.

**5. Ендпоінт не ідемпотентний.** Немає жодного механізму (idempotency key, зв'язок з
конкретною транзакцією), що запобігав би подвійному нарахуванню при ретраї мережі чи
повторному запиті. Окремо варто відзначити суперечність: за специфікацією HTTP **GET
зобов'язаний бути безпечним і ідемпотентним**, а цей не є ні тим, ні тим — тому будь-який
проміжний вузол, який має право повторити GET, повторить і нарахування.

### Суттєве

**6. Немає ledger/аудиту.** Жодного запису «хто/скільки/коли/за що» — для фінансової операції
в гемблінг-домені без цього неможливо розслідувати спірні нарахування чи коректно зробити
reversal.

**7. Немає транзакції БД.** Один `save()` зараз не критичний сам по собі, але при найменшому
ускладненні логіки (наприклад, паралельний запис у ledger) без транзакції з'явиться ризик
часткового запису.

**8. Гроші, найімовірніше, у float.** `$player->balance += $request->amount` без жодного
приведення типу означає, що сума лягає на баланс як є. Якщо `balance` — `float`/`double`,
накопичується похибка округлення й `0.1 + 0.2 != 0.3` в'їдається просто в баланс гравця.
Гроші мають бути **цілими числами в мінімальних одиницях** (центи, `bigint`), а форматування —
на межі API.

**9. `success: true` — константа, а не результат.** Поле не залежить ні від чого: гілки
помилки в методі немає взагалі. Клієнт, який перевіряє `success`, ніколи не побачить відмови,
а некоректний `amount` віддасть не помилку домену, а 500 від PHP. Потрібне явне розділення:
**422** на помилку формату, **409** (або доменний код) на порушення бізнес-правила.

**10. Відповідь неповна.** Повертається лише `balance`, без суми нарахування чи id операції —
фронтенду й аудиту нема на що спертись для звірки.

**11. Немає rate limiting** на ендпоінті, що змінює гроші.

**12. Немає тестів.** Метод рухає гроші й не має жодного. Гонка з пункту 4, від'ємна сума
з пункту 2 і повторний виклик з пункту 5 — це рівно ті випадки, які тест і має прибити,
бо очима вони не видно, а в проді коштують дорого.

## Фронтенд

**13. `axios.get` для мутації.** Дзеркалить бекенд-проблему #3 — GET використовується для
операції зі стороннім ефектом.

**14. Немає обробки помилок.** Відсутній try/catch — при падінні запиту буде необроблений
reject, UI зависне в невизначеному стані без повідомлення користувачу.

**15. Немає стану завантаження.** Кнопку нічого не блокує під час запиту — користувач може
клікнути кілька разів поспіль, що підсилює бекенд-проблему #5 (немає ідемпотентності — кожен
клік нарахує окремо).

**16. Пряма мутація `this.player.balance`**, ймовірно проп, замість `$emit` наверх. Порушує
однонапрямлений потік даних Vue.

## Як ці ж проблеми вирішені в Частині 1

Рев'ю писалось не абстрактно: майже кожне зауваження вище має відповідник у коді цього репозиторію.

| Проблема | Рішення в цьому проєкті |
|---|---|
| #1 гравець з URL | `$request->user()` під `auth:sanctum`; жоден ендпоінт не приймає id гравця ззовні |
| #2 сума без валідації | Form Request із `regex` на код; сума береться **з промокоду в БД**, а не з тіла запиту |
| #3 GET на мутацію | `POST /api/promo/claim`, `PATCH /api/promo/{claimId}/revoke` |
| #4 гонка на `+=` | `DB::transaction()` + `lockForUpdate()` у `WalletService`, плюс unique-індекси як реальна гарантія |
| #5 подвійне нарахування | частковий unique `(user_id, promo_code_id) WHERE status <> 'rejected'` і unique `(promo_claim_id, type)` на ledger |
| #6 немає аудиту | таблиця `wallet_transactions`: кожен рух балансу — окремий рядок зі знаком і `balance_after_cents` |
| #8 float на грошах | цілі центи (`bigint`) наскрізь; API віддає і `cents`, і `formatted` |
| #9 `success: true` | **422** на формат, **409** з машинним `reason` на бізнес-правило, **404** на чужий claim |
| #11 rate limiting | `throttle:20,1` на обох грошових ендпоінтах |
| #12 немає тестів | 52 тести бекенду; `SchemaGuardsTest` пише повз сервіси й доводить, що інваріанти тримає схема |
| #14, #15 фронтенд | стани `idle/loading/success/error`, guard від подвійного сабміту **в обробнику**, а не лише через `disabled` |
| #16 мутація пропа | баланс піднімається наверх через `emit`, змінює його тільки власник стану |
