# Part 2. Code review

A code fragment generated by an AI tool for a "credit a bonus to a player's balance" ticket in a
different project. Reviewed without running it — like a colleague's PR.

```php
// routes/api.php
Route::get('/players/{player}/credit-bonus', [WalletController::class, 'creditBonus']);
```

```php
// app/Http/Controllers/WalletController.php
public function creditBonus(Request $request, Player $player)
{
    $player->balance += $request->amount;
    $player->save();

    return response()->json(['success' => true, 'balance' => $player->balance]);
}
```

```js
// resources/js/components/BonusCredit.vue (a fragment of the method)
async creditBonus(amount) {
  const response = await axios.get(`/api/players/${this.player.id}/credit-bonus`, {
    params: { amount }
  })
  this.player.balance = response.data.balance
}
```

---

## Backend

### Blockers

**1. There is neither authentication nor authorisation.** The route has no middleware at all —
the endpoint is open to anyone without a token. On top of that, `Player $player` is resolved
directly from the route parameter via route-model binding. Anyone who substitutes someone else's
`player_id` in the URL can credit a bonus to an arbitrary player. The player must be taken from
the authenticated user (`$request->user()`), not from the URL — the `{player}` parameter is
unnecessary in the first place.

**2. `$request->amount` is not validated.** There is no check of type, sign or bounds.
Consequences:
- a negative number → **debits** funds instead of crediting them;
- there is no upper bound → any amount can be credited in a single request;
- a string instead of a number: in PHP 8 a non-numeric string in arithmetic throws a `TypeError`
  (i.e. a 500 instead of a validation error), while "5abc" gives a warning and a silent 5;
- a missing value → `null + number` = a warning/error depending on the PHP version.

**3. GET for a state-changing operation.** Crediting is a mutation, so it should be POST/PATCH,
not GET. The consequences of GET specifically here:
- browsers and proxies may **cache** the response;
- **prefetch** (the browser, an antivirus, a link preview in a messenger) may invoke the endpoint
  without the user's knowledge;
- the amount and the player_id end up in the **query string** → server logs, browser history, the
  Referer header;
- with **session** authentication (Sanctum in SPA mode) the endpoint becomes vulnerable to CSRF
  via an ordinary `<img src="...">`: Laravel verifies the CSRF token only on POST/PUT/PATCH/DELETE,
  never on GET. A caveat: this route lives in `routes/api.php`, where sessions and
  `VerifyCsrfToken` are not wired in at all, so with token auth the vector would not fire — but
  here there is no authorisation whatsoever (point 1), so the request is open to everyone anyway.

**4. Race condition (lost update).** `$player->balance += $request->amount; $player->save();` is a
read-modify-write without a row lock and without a transaction. Two parallel requests read the
same stale balance and one increment is lost. What is needed is a `DB::transaction()` with
`lockForUpdate()`, or an atomic `increment()`.

**5. The endpoint is not idempotent.** There is no mechanism at all (an idempotency key, a link to
a specific transaction) that would prevent double crediting on a network retry or a repeated
request. Worth noting separately is the contradiction: per the HTTP specification **GET is
required to be safe and idempotent**, and this one is neither — so any intermediary that is
entitled to repeat a GET will repeat the crediting too.

### Significant

**6. There is no ledger/audit trail.** Not a single "who/how much/when/for what" record — for a
financial operation in a gambling domain, without it you cannot investigate disputed credits or
perform a correct reversal.

**7. There is no DB transaction.** A single `save()` is not critical in itself right now, but at
the slightest complication of the logic (a parallel write to a ledger, for example) the absence of
a transaction introduces the risk of a partial write.

**8. Money is most likely a float.** `$player->balance += $request->amount` without any type cast
means the amount lands on the balance as is. If `balance` is a `float`/`double`, rounding error
accumulates and `0.1 + 0.2 != 0.3` eats straight into the player's balance. Money must be
**integers in the smallest unit** (cents, `bigint`), with formatting at the API boundary.

**9. `success: true` is a constant, not a result.** The field does not depend on anything: there is
no error branch in the method at all. A client that checks `success` will never see a refusal, and
an invalid `amount` will return not a domain error but a 500 from PHP. An explicit split is
needed: **422** for a format error, **409** (or a domain code) for a business-rule violation.

**10. The response is incomplete.** Only `balance` is returned, without the credited amount or an
operation id — neither the frontend nor an audit has anything to reconcile against.

**11. There is no rate limiting** on an endpoint that moves money.

**12. There are no tests.** The method moves money and has none. The race from point 4, the
negative amount from point 2 and the repeated call from point 5 are exactly the cases a test is
there to nail down, because they are invisible to the eye and expensive in production.

---

## Frontend

**13. `axios.get` for a mutation.** Mirrors backend problem #3 — GET is used for an operation with
a side effect.

**14. There is no error handling.** No try/catch — if the request fails there will be an unhandled
rejection, and the UI will hang in an undefined state with no message to the user.

**15. There is no loading state.** Nothing blocks the button while the request is in flight — the
user can click several times in a row, which amplifies backend problem #5 (no idempotency — every
click credits separately).

**16. Direct mutation of `this.player.balance`**, probably a prop, instead of `$emit` upwards.
This breaks Vue's one-way data flow.

## How these same problems are solved in Part 1

The review was not written in the abstract: almost every finding above has a counterpart in this
repository's code.

| Problem | Solution in this project |
|---|---|
| #1 player from the URL | `$request->user()` under `auth:sanctum`; no endpoint accepts a player id from outside |
| #2 amount without validation | a Form Request with a `regex` on the code; the amount is taken **from the promo code in the DB**, not from the request body |
| #3 GET for a mutation | `POST /api/promo/claim`, `PATCH /api/promo/{claimId}/revoke` |
| #4 race on `+=` | `DB::transaction()` + `lockForUpdate()` in `WalletService`, plus unique indexes as the real guarantee |
| #5 double crediting | a partial unique `(user_id, promo_code_id) WHERE status <> 'rejected'` and a unique `(promo_claim_id, type)` on the ledger |
| #6 no audit trail | the `wallet_transactions` table: every balance movement is a separate signed row with `balance_after_cents` |
| #8 floats on money | integer cents (`bigint`) throughout; the API returns both `cents` and `formatted` |
| #9 `success: true` | **422** for format, **409** with a machine-readable `reason` for a business rule, **404** for someone else's claim |
| #11 rate limiting | `throttle:20,1` on both money endpoints |
| #12 no tests | 52 backend tests; `SchemaGuardsTest` writes past the services and proves that the invariants are held by the schema |
| #14, #15 frontend | `idle/loading/success/error` states, a double-submit guard **in the handler**, not just via `disabled` |
| #16 prop mutation | the balance is lifted up via `emit`; only the state owner changes it |
